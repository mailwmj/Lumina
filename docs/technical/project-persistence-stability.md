# 项目持久化稳定性与性能验证

验证日期：2026-09-09。

## 范围与验收标准

本轮聚焦 `src/stores/projectStore.ts` 的项目保存、视口保存、删除和异步打开链路。

- 较旧的整项目保存和视口写入不能覆盖较新的视口。
- 存储耗时超过 800 ms 时，删除请求仍在正在进行的写入结束后执行。
- 用户新建或删除项目后，之前发起的打开请求不能重新接管活动项目。
- 持久化只编码当前节点和保留历史实际引用的图片，内存撤销历史保持原有容量。
- 连续编辑继续合并保存；仅改变视口时继续使用轻量命令。

## 实现约束

整项目和视口保留各自的防抖队列与命令，但同一项目的两类写入互斥。整项目快照包含视口，等待空闲调度的快照同样占用写入序列；较新的视口在该快照完成后写入。不同项目互不阻塞。

删除以写入完成事件驱动，不再经过最多十次、每次 80 ms 的等待轮询。标记删除后清理待写队列，阻止新的排队写入；正在进行的写入完成后触发删除。数据库命令本身失败时仍沿用现有日志处理，本轮没有引入持久化重试或新增界面提示。

新建和删除项目递增打开请求序号，沿用既有的请求失效判断。

图片池在历史裁剪之后建立，保留历史仍为前后各最多 12 步，不改变 SQLite 数据格式。序列化异常也会释放正在写入状态，避免后续排队保存被永久阻塞。

评估了项目 Store 已超过 800 行的情况。本轮保留现有模块边界，以缩小并发修复的变更范围；未同时进行文件拆分。

## 编码层对比

使用 50 步历史、每步一个独有图片字符串的合成项目，每个图片字符串约 32 KiB，当前画布使用最后一张图片。从修改前 HEAD 与工作区源码提取同一编码路径，在相同 Node.js 环境中转译运行；各预热 10 次，测量 50 次，取中位数。

| 指标 | 修改前 | 修改后 |
| --- | ---: | ---: |
| 持久化图片池条目 | 50 | 12 |
| historyJson 字节数 | 1,641,265 | 395,018 |
| 编码耗时中位数 | 3.905 ms | 0.934 ms |

样本保存数据量减少约 76%。回归测试同时断言保存体积、图片池范围，以及重新打开后当前图片与 12 步历史的恢复结果。

此结果只证明该合成样本的编码与数据量变化，不代表所有项目的收益或真实画布帧率。未运行原生 Tauri/SQLite 联调、真实大画布交互测量或打包安装验证；Rust 代码未改动。
