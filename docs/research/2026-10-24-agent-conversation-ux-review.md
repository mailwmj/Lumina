# 内置 Agent 提问与对话体验评审

日期：2026-10-24。范围：截图、当前内置 Agent 实现、公开交互设计资料与 AI SDK 官方文档。本文是待实施方案，没有修改产品代码；代码结论来自静态检查及文末列出的现有测试，没有进行应用内完整走查。

## 1. 目标与判断

用户的目标是完成图片创作、表达偏好并快速修订。提问只有在减少返工的收益大于打断成本时才有价值。

建议：卡片选项末尾固定提供“自定义…”自由输入入口；ask_user 按需调用；通常问 1–2 个问题，复杂任务单次最多 5 个；区分必须澄清的事实与可以委托 Agent 决定的偏好；回答、跳过、取消均有明确去向。

“最多 5 个”是针对当前产品的设计建议，不是研究证明的最佳数量，也不应成为问满 5 个的指标。

## 2. 当前实现的证据

| 现象 | 代码事实 | 用户影响 |
| --- | --- | --- |
| 没有自行输入 | `domain/agentTools.ts` 中 `allowCustom` 可省略，`approval-card/index.tsx` 仅在它为真时显示输入框 | 模型漏传参数即可剥夺用户表达能力 |
| 问题看起来总有 3 个 | Schema 为 1–3 个问题，工具描述及系统指令也写 1–3；没有“必须 3 个”的逻辑 | 数量上限较低，提示词同时形成数量锚点 |
| 选项只有几个 | 每题选项实际最多 6 个，与问题数量是两个限制 | 无需把选项上限从 3 改为 5 |
| 是否强制提问 | `canvasAgent.ts` 注册 ask_user，没有强制选用它；指令允许信息足够时直接动手 | 需要优化决策规则，不能归因于组件强制出现 |
| 调用后必须回答 | ask_user 没有 execute，通过 `addToolOutput` 后续跑；卡片没接跳过、关闭回调 | 工具调用可选，但调用后的等待缺少明确出口 |
| 选中后突然跳题 | 单选默认在 240ms 后前进；选择与自定义输入会相互清空 | 不便阅读、纠正或“选一项再补充” |
| 等待被标为完成 | `AgentMessageParts.tsx` 只有 streaming 时判定 working，暂停后显示 complete | 截图出现“完成 1 步”，实际仍等待回答 |
| 直接在底部回复 | `AgentConversation.tsx` 始终走新消息发送；旧未完成工具调用从模型副本中删除；旧卡片只在最后一条消息可提交 | 能继续说话，但不是明确回答原问题，额度按新用户消息重新划分 |
| 旧卡片仍像可操作 | 无 onSubmit 时，基础卡片的输入和导航仍只依据 busy 禁用 | 新消息之后的旧问题可能仍可选择，却无法真正提交 |
| 中途作答可能丢失 | 卡片答案及题号存在组件本地状态；会话切换会卸载对话组件 | 已答内容和输入可能要重填；已提交答案则正常持久化 |
| 生图期间占位不跟随真实结果 | `generateImageTool.ts` 等结果后才返回 ID；`AgentImageGrid.tsx` 在无 output 时使用虚拟占位 | 整批结束前难以逐张展示已经完成的图 |
| 错误文案不准确 | 无图片模型和额度耗尽都返回 refused，图片卡统一显示“本轮额度已用完” | 用户无法知道正确的恢复动作 |

## 3. 提问决策

先判断用户是在讨论方案、探索方向，还是明确要求生成/修改。讨论阶段不自动生图；已有执行意图且信息足够时直接执行，不增加“是否开始”确认。

| 场景 | 建议行为 |
| --- | --- |
| 明确的创作或编辑指令 | 直接执行，不重复询问已给出的条件 |
| 缺少颜色、光线等审美偏好 | 按上下文做合理选择；必要时一句话说明采用的方向后执行 |
| 缺少真实名称、活动日期、必须准确的海报文字 | 询问必要内容，不能自行编造商业事实 |
| 多张结果后说“改一下”，没有明确引用 | 用带缩略图的选择定位对象，仍允许输入“第二张”等自然语言 |
| 用户明确引用一张图，说“把这张改暖一点” | 已经明确对象，直接修改，不因上轮有多张就追问 |
| 用户说“你决定”“先出一版”“不用问” | 普通创意偏好直接决定；对象仍不明确时，只澄清对象或暂停该操作 |
| 用户要求充分沟通后再做 | 支持较完整的 3–5 题需求收集，按当前信息删掉已知问题 |

系统指令应强调“缺少信息是否导致无法正确执行”，而不是枚举用途、主体、风格、比例并容易逐项追问。默认一轮集中问清，回答后执行；出现新的实际冲突时才继续澄清，不用硬性轮数掩盖新问题。

## 4. 提问卡片

保留现有单题分页结构，避免 5 题同时撑满窄侧栏。去掉默认选中后自动跳题，改为明确的“下一题 / 继续”。题号使用 `2/5`，可以返回修改；不重复堆叠题号和装饰性进度提示。

- 每道有选项的问题末尾固定提供“自定义…”选项，点击后在卡片内展开可扩展的多行文本输入，用户可以直接填写自己的答案并提交。这个入口由 UI 添加，不依赖模型生成或 allowCustom 参数，也不占模型提供的预设选项数量；没有预设选项的开放题直接显示输入框。
- 选项是快捷回答，文字可独立作答，也可在选中后补充，例如“深色底，但不要荧光绿”。单选表示预设选项之间单选，不表示禁止补充文字。
- 不默认替用户选择第一项。建议项可以标注推荐，但必须由用户选择或明确委托。
- 问题上限从 3 放宽到 5；通常 1–2 题；每题通常 2–4 个有区分度的选项，现有 6 项上限先保留。图片选择超过上限时引导从画布引用，而不是继续铺开长列表。
- 卡片层面只提供“你来决定”（未答的题交给 Agent）和“取消”两个出口，不按题目类型区分可否跳过。让模型给每题标注“偏好 / 事实”再由界面强制，标错时用户反而无法跳过；事实保护放在指令里：委托不等于授权编造真实名称、日期，缺失时画面不放这些文字或再次说明需要补充。
- 主操作为“继续”；可按已答内容继续，未答内容交给 Agent。
- 提交期间防止重复提交；恢复失败时保留答案。提交前保留当前题与所有答案，至少跨会话切换不丢失；重启恢复作为后续项单独处理。
- 提交后收起为“配色：深色底；补充：不用荧光绿”等可读摘要，保持问题与答案对应。

示意：

```text
配色偏好？                                  2/4

○ 黑白单色
○ 深色底 + 少量亮色
○ 低饱和单色
✎ 自定义…

展开后：[ 输入自己的想法，也可以补充已选项… ]

你来决定                         上一题  下一题
```

卡片展示是可选的；一旦模型调用 ask_user，就代表需要等待用户反馈。不要让同一次工具调用一边显示“等你回答”一边继续付费生成。无需等待的审美取舍，用简短说明表达并执行即可。也不通过计时器把沉默当作同意。

## 5. 让底部输入框成为统一的对话入口

存在待回答提问时，底部仍允许自然语言回答；占位提示可变为“回答问题，或补充你的想法”。卡片与底部输入共享同一个待回答对象。

1. 用户可以只选、只写，或两者结合；底部一次回复可以回答多个问题，不强迫用户逐题对应格式。
2. 底部回复照常作为一条 user 消息发送，不改走 `addToolOutput`。这样上传与引用（`prepareAgentMessage`）、张数解析（只读最后一条 user 消息的 metadata）和用户气泡都沿用现有链路。发送时给待回答的 ask_user 写入 `answered_in_chat` 结果，模型能看到自己问过什么，并以紧随其后的用户消息作为回答。
3. 这是同一 Agent 回合的续跑：`resolveTurnBudget` 的回合起点跳过“回答待定提问”的 user 消息，已用额度自然延续。新增上传图片沿用导入画布流程，只保存节点 ID。
4. 用户在回答中明确修改张数时，以这条消息解析出的张数为准；没有明确张数时沿用回合起点消息的张数。已用额度不能清零，也不能接受模型自报的张数。
5. 提供明确的“取消本次操作”。取消只写入 `cancelled` 结果、不续跑模型（避免一次只为回复“已取消”的调用），旧卡片显示已取消且只读，再发送的需求开始新回合。
6. 卡片提交走 `addToolOutput` 续跑，底部回复走 `sendMessage`，两条路径互斥：卡片一旦有结果就不再是待回答，底部消息也就不会接回它，因此不需要额外的防重锁。

实现优先沿用 AI SDK 的工具结果与自动续跑机制；不用自建 Agent 循环。

输出契约需要表达“已回答 / 委托决定 / 在对话中回答 / 已取消”，不把空字符串伪装成回答。继续读懂已存储的旧答案结构即可，不扩展成通用表单框架，也不新增数据库表。

## 6. 整体流程的其他优化

### P0：让表达与反馈可信

- 自由输入、最多 5 题、取消自动跳题；修改 ask_user 的触发指令及工具描述。
- 等待回答显示“等你回答”，失败显示实际失败；旧卡片明确只读，不留下可点击却无效果的控件。
- 区分缺少模型、额度耗尽、提交失败、部分失败，给出对应操作。成功张数来自实际 ready 结果，不能把 grantedCount 当成成功数。
- 用户没回答就发了新消息时，不再从模型副本中删掉那次 ask_user，改为补一个“未回答”结果，模型仍能看到自己问过什么。
- 图片编号、引用缩略图与节点一一对应，用户明确引用时优先采用。

### P1：打通回答与生成的连续性

- 底部自由回复接回原提问；偏好委托、取消、作答状态与额度续接完整闭合。
- 生成节点及结果占位创建后，尽早通过 SDK 支持的进度数据发布节点 ID，卡片立即从画布读状态；逐张完成逐张展示，不等整批工具返回。继续保持图片只存节点 ID，不保存 base64。
- 保留现有“提交到供应商的任务属于节点”的语义。将“停止生成”调整为准确的“停止 Agent”，只有存在后台图片任务时补充“已提交的图片仍在生成”。真正取消供应商任务另行评估。
- 文本模型错误允许重试继续对话，图片错误复用节点重试；不得因为重试文本流再次提交已经开始的生图任务。
- “五个不同方向”要产生有差异的提示词；“同方向五张”可以复用提示词。当前 count 拆成同提示词节点，不能保证五个方向。优先复用多次 generate_image 调用，并修正“每次都传完整请求张数”的指令，使多次调用的目标总数正确。

### P2：减少额外打扰

- 参考图的关键内容影响编辑时，在动手前用已有 view_images 看图；无法看图时如实说明，不声称做过视觉判断。
- “继续修改”既有能力可保留，引用目标应清楚，键盘与触摸设备也应容易发现入口。
- 空状态示例优先填入草稿，用户可编辑后发送；当前点击立即发送，可能触发用户尚未预期的生成。
- 用户正在拖拽或浏览其他区域时不自动移动画布；提供“定位结果”。目前新结果 ID 出现后会触发 fitView，需要应用内验证打扰程度。
- 会话列表用轻量状态显示正在运行 / 等待回答 / 失败，方便切换后回来处理。
- 默认思考等级当前是 max。先测首个有效响应耗时与任务完成效果，再决定是否调整；本轮不直接改模型参数，也不另造任务分类器。

## 7. 实施边界与验证

主要改动落点：`domain/agentTools.ts`、`application/agentInstructions.ts`、`application/tools/askUserTool.ts`、`ui/AgentMessageParts.tsx`、`ui/AgentConversation.tsx`、`application/agentChatTransport.ts`、`application/turnBudget.ts` 及基础卡片；文案同步中英文。问答草稿放现有 UI store，已提交结果仍走既有会话持久化。生成进度优化单独实施，避免与第一批问答修复混在一起。

沿用画布作为图片事实源、应用层执行工具、生成新节点、SDK 管理循环、同回合额度不重置等现有约束。本次不需要新框架、新 Agent、新数据库表或全局“提问强度”设置。

最低验收场景：

| 场景 | 验收标准 |
| --- | --- |
| 信息充分的“画一只窗台上的橘猫” | 直接生成，不走固定问卷 |
| 自定义回答、选项加补充、纯开放题 | 均可提交，文字不被清空，模型收到原意 |
| 1、3、5 题 | 均可正常回退、提交；不凑题；中英文与键盘可用 |
| 用户说“你决定” | 普通偏好继续执行，不再次问同类问题 |
| 多图中明确引用一张 | 直接编辑该图，不重复询问目标 |
| 关键对象仍不明确 | 不猜图，可继续澄清或取消 |
| 问答期间底部回复 | 原回合续跑，已用额度保持，新增引用可用 |
| 回答时将三张改成五张 | 用户修改的数量生效，累计消耗不清零 |
| 切换会话后返回、重复点击提交、续跑失败 | 答案保持；只提交一次；失败可恢复 |
| 取消或被后续需求替代的旧提问 | 状态明确，只读，无悬空等待 |
| 一批图片部分成功、部分失败 | 每张状态真实，成功数量准确，已成功图不会被整批重试 |
| 停止 Agent 后任务仍在生成 | 文案真实，任务与节点保留，恢复对话不重复提交 |

效果验证关注首次可用结果耗时、首次生成前的澄清次数、问题放弃情况与得到结果后的修改情况；先用代表性任务走查，不因指标需要直接新增用户行为采集。更少提问不自动等于更好，需同时检查结果是否满足任务。

本次实际运行的检查：`npx vitest run src/features/agent/application/agentChatTransport.test.ts src/features/agent/application/turnBudget.test.ts src/features/agent/application/tools/generateImageTool.test.ts`，3 个测试文件、24 项测试全部通过。这些是现状基线测试，不能证明上述待实施交互已经可用。

## 8. 外部依据

- [Microsoft：Human-AI Interaction Design Guidelines](https://www.microsoft.com/en-us/research/blog/guidelines-for-human-ai-interaction-design/)：按任务上下文决定介入时机，支持便捷忽略、修正，并在必要时消歧。
- [Google PAIR：Feedback + Control](https://pair.withgoogle.com/guidebook-v2/chapter/feedback-controls/)：平衡自动化与用户控制，让用户能够调整输出、退出反馈，并理解反馈如何影响下一步。
- [GOV.UK：Question pages](https://design-system.service.gov.uk/patterns/question-pages/)：只问确实需要的信息，避免重复收集，允许有效的“不确定”回答。
- [GOV.UK：Radios](https://design-system.service.gov.uk/components/radios/)：不预选用户答案；必要时提供“不知道 / 都不是”，复杂条件内容需要谨慎处理。
- [AI SDK：Chatbot Tool Usage](https://ai-sdk.dev/docs/ai-sdk-ui/chatbot-tool-usage)：用户交互工具通过 addToolOutput 回填，用 sendAutomaticallyWhen 控制结果齐备后的续跑。

这些资料支持减少不必要打断和保留控制权的方向；单次 5 题、默认 1–2 题及具体卡片布局属于结合 Lumina 当前任务与侧栏空间提出的设计判断，仍需实际走查验证。
