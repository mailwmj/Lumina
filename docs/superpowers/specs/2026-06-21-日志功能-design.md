# 日志功能设计

> **日期**：2026-06-21
> **目标**：为 Storyboard Copilot Plus 添加结构化、可配置、可调试的前端日志体系，与现有后端 `tracing` 体系统一时间线持久化。
> **设计状态**：Draft，等待用户审阅

---

## 1. 背景与目标

### 1.1 现状
- **后端（Rust）**：12 个文件 / 169 处 `tracing::/info!/warn!/error!/debug!` 调用，已通过 `tracing-subscriber` + `tracing-appender` 按日滚动写入 `storyboard.log`。结构化、级别可控、统一。
- **前端（TS/React）**：20 个文件 / 160 处 `console.log/info/warn/error/debug` 直接调用，**无抽象层、无级别过滤、无持久化**。日志仅出现在 DevTools，关闭窗口即丢失。
- **CLAUDE.md 第 5.5 节** 只规定"前端 console.info/error、后端 tracing::info!"，没规定抽象或持久化。

### 1.2 目标（用户确认）
- **核心目标**：调试和开发体验
- **人群**：仅开发者本人
- **范围**：前端为主，后端做必要补充
- **可配置**：运行时可调（级别、模块过滤）
- **必备能力**：结构化字段、本地持久化、dev-only 浮动面板、全面重构现有 160 处 console.* 调用

### 1.3 非目标（YAGNI）
- 不做 OpenTelemetry / 远程上报 / 错误聚合
- 不做生产环境的运维仪表盘
- 不做用户可见的"日志中心" UI（仅开发者可见）
- 不引入新 npm 依赖
- 不引入新 Rust crate

## 2. 架构

```
┌─────────────────────────────────────────────────────────┐
│  React 组件 (160 处 console.* 调用)                    │
└─────────────────────┬───────────────────────────────────┘
                      │ logger.xxx("msg", { key: val })
                      ▼
┌─────────────────────────────────────────────────────────┐
│  src/lib/logger.ts (新建)                              │
│  - 命名空间解析 (auto from stack trace)                 │
│  - 级别过滤 (debug/info/warn/error)                     │
│  - 结构化字段序列化 (JSON)                              │
│  - 持久化 ring buffer (最近 500 条用于 UI 面板)         │
│  - 控制台输出 (带颜色)                                  │
│  - Tauri IPC 发送                                       │
└─────────────────────┬───────────────────────────────────┘
                      │ invoke("append_log", { level, target, message, fields, ts_ms })
                      ▼
┌─────────────────────────────────────────────────────────┐
│  Rust: commands/logging.rs (新建)                       │
│  - tracing::event!(target: "frontend", ...)            │
│  - 自动带 session_id 字段                              │
│  - 复用现有 setup_logging 的 file appender              │
└─────────────────────┬───────────────────────────────────┘
                      ▼
              storyboard.log (单一文件, daily rotation)
```

**关键原则**：
- **前后端日志同源**：前端日志通过后端 `tracing` 写入同一文件，以 `frontend` 命名空间区分；时间线天然对齐。
- **前端只发不存**：所有持久化走后端；前端 ring buffer 仅服务于内置 UI 面板。
- **零新依赖**：复用现有 `tracing`、`tracing-subscriber`、`tracing-appender`、Tauri IPC。

## 3. 前端 Logger API

### 3.1 文件位置与导出

新建 `src/lib/logger/index.ts` 与若干子文件：
- `src/lib/logger/types.ts` — 类型定义
- `src/lib/logger/levels.ts` — 级别常量与比较
- `src/lib/logger/config.ts` — 配置存储与读取
- `src/lib/logger/transport.ts` — 控制台 + IPC + ring buffer 三个输出
- `src/lib/logger/namespace.ts` — 调用栈解析命名空间
- `src/lib/logger/serialize.ts` — 字段安全序列化
- `src/lib/logger/index.ts` — 聚合导出
- `src/lib/logger/store.ts` — zustand store 给 LogPanel 订阅
- `src/lib/logger/LogPanel.tsx` — dev-only 浮动 UI

### 3.2 公共 API

```typescript
// 顶层 API（自动命名空间）
export const logger = {
  debug(msg: string, fields?: LogFields): void;
  info(msg: string, fields?: LogFields): void;
  warn(msg: string, fields?: LogFields): void;
  error(msg: string, fields?: LogFields): void;
};

// 显式命名空间（少数场景）
export function getLogger(ns: string): Logger;

// 配置
export function setLogConfig(cfg: Partial<LogConfig>): void;
export function getLogConfig(): LogConfig;
export function resetLogConfig(): void;
```

### 3.3 类型

```typescript
type Level = 'debug' | 'info' | 'warn' | 'error';
type LogFields = Record<string, unknown>;

interface Logger {
  debug(msg: string, fields?: LogFields): void;
  info(msg: string, fields?: LogFields): void;
  warn(msg: string, fields?: LogFields): void;
  error(msg: string, fields?: LogFields): void;
}

interface LogConfig {
  level: Level;                       // 全局最低输出级别，默认 'debug'
  moduleLevels: Record<string, Level>; // 模块级别覆盖，默认 {}
  console: boolean;                   // 是否输出到 console，默认 true
  persist: boolean;                   // 是否持久化到文件，默认 true
  consoleTimestamps: boolean;         // console 输出是否带时间，默认 false
}

interface LogEntry {
  id: string;            // uuid
  ts: number;            // Date.now()
  level: Level;
  target: string;        // 命名空间，如 "frontend.features.canvas.Canvas"
  message: string;
  fields: LogFields;
}
```

### 3.4 关键设计决策

- **自动命名空间**：`logger.info("...")` 通过 `Error().stack` 解析调用文件，转换为点分路径（`src/features/canvas/Canvas.tsx` → `features.canvas.Canvas`）。开发体验接近 Rust `tracing::info!` 的零样板。
- **结构化字段**：第二参数 `fields` 是普通对象，自动 JSON 序列化（带循环引用保护 → 字符串 `'<circular>'`）。
- **error 特殊处理**：`logger.error(msg, { err })` 中如果 `err` 是 Error 实例，自动把 `err.stack` 拼接到 message 末尾。
- **批量节流**：高频调用（如 1ms 内多次 `debug`）合并成一个 IPC 调用，避免淹没后端通道。具体：每 200ms 一次 flush buffer，单条 timeout 50ms。
- **Tauri 不可用时降级**：`typeof window.__TAURI_INTERNALS__ === 'undefined'` 时跳过 IPC，只输出 console + ring buffer。这样 Vite 单独 dev（没起 Tauri）时仍能工作。
- **同步优先**：所有 logger 方法是同步的（只是把 entry push 到内存队列和 ring buffer），不阻塞调用方。

## 4. 后端 Tauri Command

### 4.1 新建 `src-tauri/src/commands/logging.rs`

```rust
use serde::Deserialize;
use tauri::AppHandle;

#[derive(Deserialize)]
pub struct FrontendLogEntry {
    pub level: String,      // "debug" | "info" | "warn" | "error"
    pub target: String,     // 命名空间
    pub message: String,
    pub fields: Option<serde_json::Value>,
    pub ts_ms: i64,         // 客户端时间戳
}

#[tauri::command]
pub fn append_frontend_log(app: AppHandle, entry: FrontendLogEntry) {
    let session_id = app
        .state::<crate::session::SessionId>()
        .0
        .clone();
    let fields = entry.fields.unwrap_or(serde_json::json!({}));
    let enriched = serde_json::json!({
        "session": session_id,
        "client_ts_ms": entry.ts_ms,
        "fields": fields,
    });

    match entry.level.as_str() {
        "debug" => tracing::debug!(target: "frontend", ns = %entry.target, data = %enriched, "{}", entry.message),
        "info"  => tracing::info!(target:  "frontend", ns = %entry.target, data = %enriched, "{}", entry.message),
        "warn"  => tracing::warn!(target:  "frontend", ns = %entry.target, data = %enriched, "{}", entry.message),
        "error" => tracing::error!(target: "frontend", ns = %entry.target, data = %enriched, "{}", entry.message),
        _ => {}
    }
}
```

### 4.2 注册（在 `lib.rs` 现有 `tauri::Builder::default().invoke_handler(...)`）

```rust
.invoke_handler(tauri::generate_handler![
    // ... 现有命令
    commands::logging::append_frontend_log,
])
```

### 4.3 `SessionId` 状态

新建 `src-tauri/src/session.rs`：

```rust
pub struct SessionId(pub String);

impl SessionId {
    pub fn new() -> Self {
        Self(uuid::Uuid::new_v4().to_string())
    }
}
```

在 `run()` 的 `.setup(|app| ...)` 中注册：`app.manage(SessionId::new());` 并 `info!("session_id = {}", session_id.0);` 写入启动日志（便于关联前后端）。

### 4.4 关键点
- `target: "frontend"` 让 `env-filter` 可用 `frontend=debug` 单独控制。
- `ns` 字段为前端传入的命名空间，最终日志格式形如 `2026-06-21T10:30:01.234Z  INFO frontend{ns=features.canvas.Canvas data=...}: message`。
- 复用 `setup_logging()` 的 file appender，**不引入新文件**。
- 不写新 crate。

## 5. 持久化与轮转

- **后端**：`{app_data_dir}/logs/storyboard.log.<YYYY-MM-DD>`，按日滚动，沿用现有 `tracing-appender::rolling::daily`。
- **清理策略**：启动时检查日志目录，删除 14 天前的文件（在 `setup_logging()` 末尾加一个 `cleanup_old_logs(&log_dir, 14)`）。
- **前端 ring buffer**：500 条循环覆盖，仅用于内置 UI 面板（不持久化）。
- **日志路径**：由现有 `resolve_log_dir()` 处理跨平台 fallback（macOS `~/Library/Logs/`、Windows `%TEMP%/storyboard-copilot/logs/`、当前目录 `logs/`）。

## 8. 现有 160 处 console.* 重构

### 8.1 策略

1. **批量替换**（脚本）：
   - `console.log(` → `logger.debug(`
   - `console.info(` → `logger.info(`
   - `console.warn(` → `logger.warn(`
   - `console.error(` → `logger.error(`
   - 替换多行 `console.xxx(` → `logger.xxx(`（含模板字符串）
2. **命名空间清理**（80% 自动）：自动推断已足够，无需手动改
3. **少数显式命名空间**：在 `imageData.ts`、`canvasStore.ts` 等需要清晰归属的，改用 `const log = getLogger("canvas.imageData"); log.info(...)`
4. **特殊保留**：
   - React 内部 prop 校验（库调用）
   - Vite/HMR 错误覆盖（必要）
   - `console.error` 在 Promise 拒绝的最后兜底

### 8.2 ESLint 规则

- 在 `.eslintrc` 添加 `"no-console": "warn"`，**警告不强制**（避免破坏 dev workflow）
- 注释 `// eslint-disable-next-line no-console` 仅保留给真需要的场景

### 8.3 验证

## 9. 错误处理与降级

| 失败场景 | 行为 |
|---------|------|
| Tauri IPC 不可用（Vite 单独 dev） | 静默降级到 console + ring buffer，跳过 IPC |
| 后端 `append_frontend_log` panic/超时 | 客户端捕获，下次 1 秒后重试（指数退避 1s/2s/5s/10s 上限）|
| Ring buffer 写入失败（内存不足等） | 丢弃最旧条目 |
| localStorage 写入失败 | 内存配置仍生效，仅不持久化 |
| 字段序列化循环引用 | 转换为 `'<circular>'` 字符串，不抛错 |
| 日志面板打开但 ring buffer 为空 | 显示空状态文案"暂无日志" |
| 命名空间 stack trace 解析失败 | fallback 到 `"unknown"` |

## 13. 风险与权衡

| 风险 | 缓解 |
|------|------|
| 自动命名空间推断有性能开销（每次 `Error().stack`） | 调用频率不高；超过 1ms/次 才有问题；可加 benchmark 验证 |
| 替换 160 处 console.* 引入回归 | 增量替换：先核心模块（store/Canvas），跑全链路再扩 |
| 浮动面板遮挡画布交互 | 默认隐藏，关闭按钮在标题栏；小尺寸默认 |
| session_id 跨重启变化 | 接受；启动日志包含 session_id 可关联 |
| 现有 169 处 Rust tracing 调用是否仍要保留 | 是；不替换，仅新增前端入口 |
| 字段序列化大对象（图片 base64）拖慢日志 | 序列化前检查大小（>10KB 截断 + 标记 truncated） |
| Tauri invoke 失败导致前端日志全丢 | 降级到 console；ring buffer 仍可用 |
